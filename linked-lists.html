🔗 Linked Lists

Items that aren't stored side by side. Each one simply remembers where the next one is.

Everyday picture: a treasure hunt. You're only given the first clue. That clue tells you where to find the second, and so on, until the last clue says "that's it". To add a new clue at the start, you just write it and point it to the old first clue — nobody else has to move.

How it works

  1. Each node has two parts: a value and a "next" pointer to the following node.
  2. We only keep hold of the head — the first node. Everything else is reached by following the arrows.
  3. Adding to the front is instant: make a new node, point it at the old head, call it the new head. No shifting!
  4. Finding something is slow: there's no "jump to number 5". You must walk from the head, one node at a time.

Real life

⚡ LRU caches
The "most recently used" order is often kept in a doubly linked list next to a hash table. Java's LinkedHashMap does exactly this.
🎶 Music player
Each song knows which comes next, so adding a song in the middle is cheap.
🧠 Memory manager
Operating systems chain together free blocks of memory in linked lists.

Time & space complexity

n = number of items. Best / average / worst describe how lucky or unlucky the input is.

OperationBestAverageWorst
Add / remove at the frontO(1)O(1)O(1)
Add at the endO(n) (O(1) with a tail pointer)O(n)O(n)
Find a valueO(1)O(n)O(n)
Read item number kO(1) (k = 1)O(n)O(n)
Remove a node you already holdO(1)O(1)O(1) (doubly linked)
Space (storing n items)O(n)O(n)O(n)

Space: still O(n), but each item carries a "next" pointer on top of its value, so a linked list uses more memory per item than an array. Nodes also sit scattered in memory, which is slower for the computer to walk through than neighbouring slots.

Use it when you add and remove at the ends a lot and rarely need "give me item number k".
Avoid it when you need fast lookups by position — an array is far better.
