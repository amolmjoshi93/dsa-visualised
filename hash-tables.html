🗂️ Hash Tables

Look things up by name instead of by position — and get the answer almost instantly, even among millions of entries.

Everyday picture: a cupboard with 7 labelled drawers. A simple rule tells you which drawer each name belongs in. To find "Meera", you don't open every drawer — you apply the rule, open exactly one drawer, and look inside. That rule is the hash function.

Try it: a phone book with 7 drawers

Our rule: add up the character codes of the name, then take the remainder after dividing by 7.

Add a contact or look one up.
Tip: add many names. When two names land in the same drawer it's called a collision — they just share the drawer (a small chain).

How it works

  1. The hash function turns a key into a number. Same key, same number — every time.
  2. That number picks a bucket (drawer). Storing and finding both go to the same bucket.
  3. Collisions happen when different keys hash to the same bucket. We keep a short list inside each bucket and check just those few.
  4. Good tables stay roomy. If buckets fill up, real hash tables grow and re-spread everything, so each bucket stays short.

Time & space complexity

n = number of items. Best / average / worst describe how lucky or unlucky the input is.

OperationBestAverageWorst
Store (insert)O(1)O(1)O(n) (everything collides)
Look up by keyO(1)O(1)O(n)
Delete by keyO(1)O(1)O(n)
Items in sorted order—n/an/a
Space (storing n items)O(n)O(n)O(n)

Space: O(n) for the entries, plus spare empty buckets. That wasted room is the price of speed: a table kept about half-empty has very few collisions, so lookups stay near O(1). Packing it fuller saves memory but slows everything down.

Use it when you look things up by a key (names, IDs, words) and don't care about order.
Avoid it when you need things in sorted order or "all keys between A and F" — use a tree.
