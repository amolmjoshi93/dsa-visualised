✂️ Binary Search

If the list is sorted, you can throw away half of the remaining items with every single look. That's astonishingly powerful.

Everyday picture: the number-guessing game. "I'm thinking of a number from 1 to 100." You say 50. "Higher." Now you know it's 51–100 — half the possibilities vanished with one guess. You say 75. "Lower." And so on. You'll always get it within 7 guesses. A dictionary works the same way: you open it in the middle, see you've gone too far, and flip back.

Try it

Compare with linear search on the same kind of list: it would have taken up to 20 steps here. Binary search needs at most 5.

How it works

  1. Requirement: the list must be sorted. (See the sorting algorithms.)
  2. Look at the middle item.
  3. Equal to your target? Done. Target is bigger? Ignore the left half. Smaller? Ignore the right half.
  4. Repeat on the half that's left until you find it or nothing is left.

In code (JavaScript)

function binarySearch(sorted, target) {
  let lo = 0, hi = sorted.length - 1;
  while (lo <= hi) {
    const mid = Math.floor((lo + hi) / 2);
    if (sorted[mid] === target) return mid;
    if (sorted[mid] < target) lo = mid + 1;   // discard left half
    else hi = mid - 1;                        // discard right half
  }
  return -1;
}

Real life

📖 Dictionary & phone book
Open in the middle, decide which side, repeat.
🐛 git bisect
Finds the commit that introduced a bug by repeatedly halving the history.
🗄️ Database indexes
Sorted indexes let a database narrow down millions of rows in a handful of steps.
🎚️ Debugging by halving
"Does the bug happen before or after this line?" — same idea.

Time & space complexity

CaseSpeed
BestO(1) — the middle item is the target
Average / worstO(log n)
Cost of sorting firstO(n log n) — worth it if you search many times

Use it when the data is sorted (or you can sort it once) and you search it many times.
Avoid it when the data is unsorted and changes constantly — keeping it sorted costs more than it saves. A hash table may be better.
